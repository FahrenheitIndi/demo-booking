### Часть 2. Доработка

Исправьте `store` и `destroy` так, чтобы выполнялись правила:

## API

Все методы требуют заголовки `Authorization: Bearer <токен>` и `Accept: application/json`. Без `Accept` запрос без токена вернёт 500 вместо 401.

| Метод | Адрес | Что делает |
| --- | --- | --- |
| GET | `/api/bookings` | Мои брони |
| POST | `/api/bookings` | Создать бронь |
| DELETE | `/api/bookings/{id}` | Отменить бронь |
| GET | `/api/rooms/{room}/bookings/today` | Брони комнаты на сегодня |

Пример:

```sh
curl -X POST http://localhost:8000/api/bookings \
  -H "Authorization: Bearer anna-token" \
  -H "Accept: application/json" \
  -H "Content-Type: application/json" \
  -d '{"room_id": 1, "title": "Планёрка", "starts_at": "2026-11-02T10:00:00+03:00", "ends_at": "2026-11-02T11:00:00+03:00"}'
```

Автор брони — владелец токена, `user_id` в теле игнорируется. Время принимается в ISO 8601 с любым смещением и хранится в UTC.

Ответы `POST /api/bookings`:

| Код | Когда |
| --- | --- |
| 201 | Бронь создана, в теле — запись |
| 409 | Комната занята в это время |
| 422 | Ошибка валидации: формат полей, шаг 15 минут, длительность до 4 часов, рабочее время 09:00–20:00 по времени офиса комнаты. В `errors` — поле и сообщение |

Ответы `DELETE /api/bookings/{id}`: 204 — отменено, 403 — бронь чужая, 404 — нет такой брони.

Лог созданных броней пишется в `storage/logs/bookings.log`.

## Как решена гонка

Правило «брони одной комнаты не пересекаются» реализовано одним ограничением PostgreSQL (миграция `add_no_overlap_constraint_to_bookings_table`):

```sql
ALTER TABLE bookings ADD CONSTRAINT bookings_no_overlap
EXCLUDE USING gist (room_id WITH =, tsrange(starts_at, ends_at, '[)') WITH &&)
```

Приложение не делает `SELECT` перед вставкой: оно просто вставляет, а при нарушении ограничения (SQLSTATE `23P01` с именем `bookings_no_overlap`) превращает `QueryException` в `RoomUnavailableException` и отдаёт 409. При двух одновременных запросах на один слот PostgreSQL придержит вторую транзакцию до коммита первой и затем отклонит её — двойная бронь невозможна ни при каком порядке запросов. Полуоткрытый интервал `[)` разрешает встречи «впритык». Непересекающиеся брони одной комнаты друг друга не ждут.

Почему именно так, а не блокировкой:

- `SELECT … FOR UPDATE` строки комнаты или `pg_advisory_xact_lock(room_id)` тоже решают гонку, но сериализуют все брони комнаты, включая непересекающиеся, и защищают только тот код, который не забыл взять блокировку. Ограничение в БД нельзя обойти ни сидером, ни консольной командой, ни будущим контроллером.
- Проверка в коде плюс ограничение в БД — это два описания одного правила, которые могут разойтись. Одного ограничения достаточно, а 409 из него получается тем же путём, что и при последовательных запросах, поэтому покрыт обычными тестами.

Деплой на существующие данные: старый код допускал пересечения, и `ADD CONSTRAINT … EXCLUDE` упадёт на первой же паре. Перед миграцией найти и разобрать нарушителей:

```sql
SELECT a.id, b.id FROM bookings a
JOIN bookings b ON a.room_id = b.room_id AND a.id < b.id
WHERE tsrange(a.starts_at, a.ends_at, '[)') && tsrange(b.starts_at, b.ends_at, '[)');
```

Ограничение строит GiST-индекс под `ACCESS EXCLUSIVE`, на большой таблице это короткое окно без записи в `bookings`.

Что учесть при развитии: если появится мягкое удаление броней, в ограничение надо добавить `WHERE (deleted_at IS NULL)`; если рабочие часы станут полем офиса — это не влияет на ограничение, только на валидацию.
